Method: Cloudflare security-audit skill (github.com/cloudflare/security-audit-skill), profile **quick**, source ref b2de4f7 (clean). Run status: **complete (quick profile, partial coverage by design)**.

## Coverage statement
This is a quick-profile run: one hunter wave of 5 isolated hunters, one post-wave coverage critic, and one fresh independent verifier per candidate. It is partial coverage, not an exhaustive audit. No prior run existed. 10 coverage units: 5 covered, 2 produced candidates, 3 deferred (critic discoveries the quick profile does not hunt). Deviation from the skill: reconnaissance was done by the parent from source instead of the four baseline reconnaissance agents.

Execution: target code was **not executed**. The macOS sandbox enforced no-network (including DNS), scratch-only writes and CPU/file limits, but macOS cannot enforce a memory limit, so the skill's execution-safety rule forbids running target code. All results are source analysis; nothing could reach `confirmed`, which requires a bounded local observed result.

### Needs validation: Unauthenticated GET / gives the API session token to any local OS user, who can then read and change every saved key
Fingerprint `mcpcreds.py/make_server/root-page-discloses-session-token`. See NEEDS-VALIDATION.md.

### Rejected: Disconnect writes the whole stored credential (all parts) into AI app config env, even for wrappers that never held an inline secret
Fingerprint `mcpcreds.py:_unwrap:full-store-value-written-to-config-env`. Reason: This is not a security boundary crossing. (1) The first trace entry is not a lower-trust entrypoint. Only the authenticated local user can run Disconnect (CLI, or the token-gated POST /api/apps/undo at lines 844 to 845). No website, MCP client, LLM tool or other OS user can reach undo_app. (2) The sink writes into the user's own AI app config, and restoring tokens inline there is the documented intent (docstring at line 739, README line 76, the targeted-restore test at test_mcpcreds.py:294). For wrappers that connect_app created, each key holds exactly the single inline value it took (connect_app and _free_name), so the result matches the file's state before Connect. (3) _write_cfg never broadens permissions (line 559 keeps the existing mode). Any cross-user readability comes from the AI app's own config mode and the home-directory mode, which is the plaintext-under-file-permissions baseline the architecture accepts. (4) The extra-parts case needs the user to edit a key into a multi-part value after Connect, or to hand-write a wrapper and then choose Disconnect themselves. That is the user moving their own secret into their own file. The missing value_part call in _unwrap is a real functional and data-minimization bug: the restored server gets every line instead of the one part it needs. The fix is env[var] = value_part(items[key]["value"], var). It is not an exploitable vulnerability. Source alone settles this; target code was not executed.

## Deferred coverage (not audited in this run)
- **mcpcreds.py#DesktopApi.export_json + ui.html export (blob download, line 818-821) + main 'export' CLI** (ATTACK-CLASSES.md#Feature abuse and data leakage): No unit checked the full-secret export paths. DesktopApi.export_json (mcpcreds.py:902-910) writes every value with Path(path).write_text and never chmods, so the file gets the umask mode (often 0644) in a folder the user picks. The browser fallback (ui.html:821) saves a blob to the browser's download folder. The CLI 'export' (line 988-989) prints the whole store. The config-files unit selected the Export block, but its checks only covered the backup mode. Whether export output drops below the 0600 store invariant for other OS users (in scope per SECURITY.md) has not been checked.
- **mcpcreds.py#cmd_prefix + _our_entry + connect_app wrapped command (HTTP /api/apps/connect and CLI connect)** (ATTACK-CLASSES.md#Chained vulnerabilities and trust boundaries): Protected resource (3), 'what program a rewritten config launches', has no unit for the program MCP Creds itself writes. The existing checks only show that the ORIGINAL command is kept. cmd_prefix (lines 460-464) persists sys.executable plus the resolved __file__ into every connected app config. location_warning (467-473) flags /tmp/, /private/var/folders/, Downloads and uv archive paths, but it is advisory only: neither connect_app nor the CLI connect (default: all installed apps) refuses. Not yet checked: whether the persisted interpreter or script path can sit in a location that a lower-trust local user can write (shared /tmp parents, a non-standard python3 or venv, an unsigned or ad-hoc-signed .app outside /Applications), which would let that user later run code as the victim and receive the injected keys.
- **mcpcreds.py#delete_item + undo_app/_unwrap + _backup retention** (ATTACK-CLASSES.md#Resource and file handling): The Deletion block was selected on the config-files unit, but none of its local_checks covers deletion. delete_item (mcpcreds.py:168-175, reached from HTTP DELETE, the CLI rm and the UI) removes the store entry only. The inline tokens that connect --secure moved stay in backups/<app>-original.json, which is never overwritten or purged (line 516), and in -previous.json. _unwrap (lines 711-735) silently drops env vars whose key was deleted. Still unchecked: whether docs or the UI promise that deleting or rotating a key removes it, and whether the retained copies break that promise.

## Hardening notes (not findings)
- (h-web-api) mcpcreds.py:803-805 _body: a negative Content-Length (for example -1) is truthy, so rfile.read(-1) reads until the peer closes. This only ties up one ThreadingHTTPServer thread, and only after _authed has passed, so it is a same-principal effect; clamping n to >= 0 with an upper bound would make it robust.
- (h-web-api) mcpcreds.py:872 ThreadingHTTPServer inherits allow_reuse_address=True from HTTPServer. On Windows, SO_REUSEADDR semantics differ from POSIX; consider setting SO_EXCLUSIVEADDRUSE on Windows so another process cannot bind the same loopback port. Not reported: whether this is cross-account exploitable depends on the Windows version and socket-security defaults, and it was not observable here.
- (h-web-api) ui.html:741-745 highlight() escapes only & and <; this is safe today because the input is a server-generated command snippet in element-content context. If the input ever includes attacker-controlled text or is moved into an attribute, it should also escape > and quotes.
- (h-mcp) mcpcreds.py:225-227: the get_credential case-insensitive fallback silently picks one entry when stored names differ only in case (for example GITHUB_TOKEN and github_token), so a model could be handed a different credential than it asked for. Suggested fix: return an error listing the candidate names when more than one key matches case-insensitively, or reject case-only duplicate names in check_name.
- (h-mcp) Design note: secrets that `connect --secure` moves out of other MCP servers' configs become readable through get_credential by any connected app's model, which could be influenced by prompt injection. This is documented (README.md:128), but it widens who sees each token compared with each server's own env. Suggested fix: an optional per-item 'mcp_visible' flag (default off for migrated tokens) checked in call_tool before returning a value, while still letting `run -e` inject the token.
- (h-mcp) serve_mcp (mcpcreds.py:295) returns str(e) for unexpected exceptions. It currently leaks only local paths or parse positions, but a generic message with details on stderr would keep future exception types from echoing data to the model.
- (h-run) mcpcreds.py:389-392 _cmd_quote does not neutralise %NAME% expansion: cmd.exe expands percent variables even inside double quotes in phase 1. It also does not reject CR/LF, which can end or cut the cmd.exe /c line. Arguments come from the user's own config, so this is the same principal. Fix: reject or caret-escape '%' (outside quotes, or with a BatBadBut-style escape) and refuse arguments containing '\r', '\n' or NUL before building the cmd.exe line at line 399. Regression test: _run_windows with an arg '%PATH%&x' and a newline arg; assert the arg is rejected or the line is literal.
- (h-run) mcpcreds.py:379 on Windows, shutil.which searches the current directory before PATH unless NoDefaultCurrentDirectoryInExePath is set. Setting env['NoDefaultCurrentDirectoryInExePath']='1' for the lookup (or resolving only against PATH entries) removes the planted-.cmd-in-project-cwd route. This is parity with the AI apps' own launchers today, but cheap defence in depth. The same applies to shutil.which('clip') in copy_to_clipboard at mcpcreds.py:881.
- (h-run) mcpcreds.py:348 explicit '-e VAR' names are not checked against ENV_RE (only --all filters at line 361). Checking them would turn the uncaught ValueError on an empty or invalid name into a clear error, and would block loader-control names (DYLD_*, LD_PRELOAD, NODE_OPTIONS) set from store values by an edited config.
- (h-run) mcpcreds.py:943 main() strips every argv element starting with '-psn_', including args after 'run --' meant for the child. Limit the filter to argv[0..1] or to non-run modes so child argv is passed through exactly.
- (h-config-files) locked(): stale-lock removal (mcpcreds.py lines 101 to 102) and the unconditional unlink in finally (line 114) can break or delete a lock another process holds. Write a pid/nonce into the lock file and unlink it only if it is still ours. Use the lock file's own mtime refreshed while the lock is held, or fcntl/msvcrt locking.
- (h-config-files) _write_cfg: the fingerprint check (line 549) and os.replace (line 562) are not atomic, and mtime_ns+size misses a same-size rewrite on coarse-mtime filesystems. Compare a content hash re-read just before replace to narrow the lost-update window.
- (h-config-files) _backup: shutil.copyfile (line 519) follows a pre-existing symlink at the backup path, and the original backup's exists() check is TOCTOU. Open the target with O_CREAT|O_EXCL|O_NOFOLLOW, mode 0600, so it is never created with umask mode first.
- (h-config-files) _is_wrapped (line 585) does not check that run comes before --, so _unwrap's args.index('--', i) can raise ValueError and abort Disconnect for that app.
- (h-config-files) save()/_backup swallow chmod OSError. If MCPCREDS_HOME points at a directory owned by someone else, the store is still written there. Refuse a home dir that is not owned by the current uid or not 0700.
- (h-config-files) Deleting a key from the store does not remove copies in backups/<app>-original.json, which is kept forever (0600, same user only, and no deletion guarantee is documented). Consider documenting this or offering a purge.
- (h-supply-chain) release.yml line 7 grants contents: write at workflow level, so the test and build jobs, which run repository tests and third-party PyPI build tools, also hold a write-scoped GITHUB_TOKEN. Fix: set top-level permissions: contents: read and grant contents: write only on the publish job.
- (h-supply-chain) packaging/build.sh lines 10, 16 and 18 resolve pillow, pyinstaller and pywebview (plus transitive deps) unpinned from PyPI on every release build, and those deps are bundled into shipped binaries. Fix: pin versions with hashes (uv lock or a requirements file with --require-hashes) to bind release contents to reviewed inputs.
- (h-supply-chain) Workflow actions are pinned to mutable major tags (release.yml lines 12, 13, 27, 28, 47, 56 and 58; ci.yml lines 11 and 12). The third-party actions astral-sh/setup-uv@v6 and softprops/action-gh-release@v2 run in jobs with contents: write. Fix: pin to full commit SHAs.
- (h-supply-chain) actions/checkout in release.yml (lines 12 and 27) persists the write token in .git/config during the build. Fix: set persist-credentials: false, because the build needs no git push.
- (h-supply-chain) Releases ship without checksums, SLSA/GitHub artifact attestations or a real code signature. build.sh line 27 ad-hoc signs the macOS app and swallows codesign failure with || true. So users downloading from releases/latest (docs/index.html line 398) cannot verify artifact identity independently of GitHub. Fix: add actions/attest-build-provenance and publish SHA256SUMS.
- (h-supply-chain) Tag-protection or ruleset settings for v* tags, and who may run workflow_dispatch on a tag ref, are not visible in source. Those settings decide which repository writers can publish a release.
